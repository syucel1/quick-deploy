From visibility to delivery

Six milestones. A practical route to faster demo releases.

6 milestones · priorities follow pilot feedback

01Delivered

Inventory & visibility

A dependable map of applications, instances and Linux hosts.

  • Create and edit servers, applications and instance mappings in the UI; import and export YAML.
  • Validate inventory and save atomically with revision conflict protection.
  • Inspect systemd state, installed and running versions, and health through read-only SSH checks.
  • Show stale observations, version mismatches and missing SSH configuration explicitly.
CURRENT OUTCOME

Inventory and discovery are implemented and covered by automated checks. Deployment actions in Overview remain simulations.

Dependencies & scope +

Available now. Real server connectivity and endpoint contracts still need a pilot.

02Next

Validate against the real estate

Prove the read-only workflow with representative demo services.

  • Configure reader SSH profiles, allowed hosts and verified host keys for pilot servers.
  • Confirm systemd units, installation paths, application/instance identities and version endpoints.
  • Exercise unreachable hosts, unhealthy services, permission failures and version mismatches.
  • Document the service version contract and agree rollout, health-check and restart conventions.
SUCCESS CRITERIA

a pilot application shows trustworthy installed/running versions and health across its real demo instances.

Dependencies & scope +

Requires demo host access and a representative service with version and health endpoints.

03Next

Verified TeamCity artifacts

Turn a build link into a reproducible deployment input.

  • Connect to an approved TeamCity base URL using backend-managed credentials.
  • Resolve the exact application, build ID and artifact path from a submitted build link.
  • Download packages into backend artifact storage; record version, commit, checksum and size.
  • Show real import progress and failures, verify expected checksums where available, and reject incomplete downloads.
SUCCESS CRITERIA

a selected immutable build can be imported, verified and retrieved from the artifact library with traceable build metadata.

Dependencies & scope +

Requires TeamCity API access, artifact conventions, storage and a retention policy.

04Planned

Install, replicate & restart

Make the full deployment workflow real, observable and recoverable.

  • Add durable deployment jobs with an inventory snapshot, target selection and per-instance locks.
  • Install a versioned release on an initial target, then distribute the same verified package to the remaining targets while preserving instance configuration.
  • Activate release directories and orchestrate systemd restarts with bounded parallelism, timeouts and post-restart health checks.
  • Stream per-server and per-instance progress; support retrying failed steps, controlled cancellation and rollback to a known release.
SUCCESS CRITERIA

a representative full demo deployment finishes within the one-hour target, including health verification, and failure recovery is demonstrated.

Dependencies & scope +

Requires pilot acceptance, verified artifacts, deployment permissions and agreed rollback semantics.

05Later

Operate & collaborate

Prepare QuickDeploy for a shared, supported team service.

  • Provision Linux hosting, TLS/reverse proxy configuration, managed secrets and persistent data outside application releases.
  • Add monitoring, actionable errors, backup/restore procedures and recovery checks for interrupted jobs.
  • Introduce authentication, roles and an audit trail for inventory changes and deployment actions.
  • Add scheduled discovery and drift notifications; evaluate PostgreSQL for shared job state and multi-backend coordination while retaining YAML inventory ownership.
SUCCESS CRITERIA

agreed access controls, recovery procedures and operational monitoring are verified before broader shared use.

Dependencies & scope +

Authentication and audit trails remain deferred from the initial local/trusted demo version; shared use needs an agreed access boundary.

06Future

Container deployment support

Extend the deployment model when the applications are ready.

  • Package suitable services as containers and define image/version identity conventions.
  • Add registry integration and a container deployment adapter alongside systemd support.
  • Reuse inventory relationships, health checks, progress reporting and rollback concepts.
  • Evaluate the required container runtime or orchestration platform after a service pilot.
SUCCESS CRITERIA

a containerised pilot service can be deployed and recovered through the same application/instance workflow.

Dependencies & scope +

Requires a separate containerisation decision and pilot. Current demo services continue to use Linux/systemd.

How we’ll get there

Practical defaults that keep releases understandable and recoverable.

  • Prove read-only visibility before enabling service-changing operations.
  • Keep installed versions, running versions and historical observations distinct.
  • Preserve instance configuration; keep credentials outside inventory YAML.
  • Build for partial failures, explicit outcomes and practical recovery.
  • Measure the full deployment, including health verification, against the one-hour target.

Where we are today. Inventory editing and read-only discovery are implemented. Real discovery needs configured SSH profiles, host keys and service endpoints. Overview remains a deployment simulation: TeamCity downloads, installation, replication and restarts are future work. The delivered foundation does not imply production readiness or validation against live servers.

QuickDeploy helps development teams deploy application artifacts across multiple servers, manage application inventories, and discover running versions and service health. It is designed to speed up demo releases and sanity testing.
